# VITA — Canada Recruitment Service Layer (Stage 8) — Design

Status: derived from the owner's brief `Canada_Job_Search_System_Claude_Prompt_Blank_Details.md` (uploaded 2026-10-31) and the gap analysis against the built platform; the owner's standing instruction ("finish what you start") covers the pure-code part. Items that need owner credentials, legal opinions or conflict with safety/legal rules are listed in §8 and are NOT built.
Code: `trust-crm/`. Additive only; same branch/PR #8 until merged.

## 1. Goal
Close the gaps between the built VITA job-search module and the brief's service model: a candidate reference (CAN-YYYY-NNNN), a Canadian-format CV generator with versioned PDF/DOCX files, PDF and Excel reports (including the candidate "Canada Job Search Activity Report"), a richer employer record with contact history and an opt-out suppression list, the six-way vacancy classification and match bands with accept/reject, and service contracts with a **legal-review gate that blocks any candidate fee until a review is recorded**. Everything stays factual: no invented CV content, no fabricated LMIA or employer claims, no send without the existing consent + approval rules.

Hard rules (unchanged): CV text is built only from the candidate's **confirmed** profile; anything missing is flagged, never invented; no photo, age, marital status or other unnecessary personal data in a CV; sending stays governed by consent, approval, caps and the guard; all numbers in reports come from real rows; no PDF/Excel output contains other candidates' data; downloads are scoped like every other candidate file.

## 2. Candidate reference and fields (migration 025)
`candidates` gains (all nullable, additive): `reference text unique` (CAN-YYYY-NNNN from a locked counter, assigned on first use or by backfill for existing rows by creation year), `city`, `phone` already exists in 001? (check) / `whatsapp`, `work_authorization_status` (none|study_permit|work_permit_open|work_permit_employer_specific|pr|citizen|unknown), `relocation_ready bool`, `desired_province text`, `service_start_date date`. Staff edit through existing candidate routes with audit; candidates see their own reference and statuses. The brief's profile tabs are covered by the existing console candidate view plus new "Canadian CV", "Reports" and "Contract" sections (Tasks 3, 5, 7).

## 3. Canadian CV generator (Task 2)
Input: `js_profiles.confirmed` (+ preferences). Output model: contact (name, city/country, email, phone — only if confirmed), professional summary (template-built from confirmed facts, e.g. "{profession} with {years} years of verified experience in {skills}" — only when those facts exist), experience (as confirmed, reverse-chronological), skills, education/training, certifications/licences, languages; Canadian conventions (no photo/age/marital/nationality line unless the candidate asks). Missing sections are listed in `missing[]` and shown to staff; generation is refused when the minimum (name + at least one experience or education entry) is absent. Files: PDF and DOCX, named `<reference>-CV-V<n>.pdf|docx`, stored in the private storage as `js_cv_files` rows with kind `canadian`, version n per candidate, status draft → staff-approved → candidate-authorised (both recorded; only approved+authorised versions can be attached to applications; originals untouched). Optional French labels (section headings only; content is not translated — no machine translation of facts). Libraries: pinned, at least two weeks old, no install scripts; rendering unit-tested by extracting text from outputs.

## 4. Reports and exports (Task 3)
- Company reports (daily, weekly, monthly, custom range) and per-candidate reports in **PDF and XLSX**; same numbers as `reportService` (tests compare to raw SQL); display timezone from a new setting `report_timezone` (default `HR_TIMEZONE`/Africa/Tunis), UTC kept internally.
- "Canada Job Search Activity Report" per candidate: reference, period, activities completed, verified list of applications **actually sent** (employer, position, date, status, evidence reference), pending, replies, interviews, next planned actions; header with company facts only when configured (`FIN_COMPANY_*`/`SITE_*`); disclaimer that it promises no job, LMIA, permit or visa; candidates can download their own; staff can generate for any candidate in scope.
- Snapshots (`js_report_snapshots`: kind, period, scope, generated_by, payload hash, file key) and a scheduler job that creates daily/weekly/monthly company snapshots when enabled (`REPORT_SCHEDULE_ENABLED`, default false). CSV exports stay.

## 5. Employers, contact history, opt-out (Task 4)
`js_employers` gains: province, city, industry, phone, recruiter_contact_name, source_urls jsonb, eligibility_note, status (new|verified|contacted|replied|opted_out|blocked), last_verified_at, notes (staff-only). Contact-history endpoint and panel (all applications/messages/replies for an employer, scoped) shown before drafting a new application. **Suppression list** `js_suppressions(email/domain, reason, source, created_by)`: populated automatically when an employer reply is classified as an opt-out/unsubscribe and manually by staff; the pre-send guard refuses any send to a suppressed address/domain and marks the employer `opted_out`. Each outreach records its basis (`outreach_basis`: published_vacancy_application | employer_requested | other_documented) — only the first is allowed by the guard in this stage. No outreach without an advertised vacancy (see §8).

## 6. Vacancy classification and matching (Task 5)
`js_jobs.classification` (verified_active | foreign_applicants_stated | eligibility_unclear | work_authorization_required | prospective_no_vacancy | closed_unsuitable) derived from existing signals (status, employer-support label quoted evidence, ad text) and editable by staff with audit; **`foreign_applicants_stated` requires a quoted evidence string** (the stricter rule of DECISIONS #1 stays: the label is informational, never proof of LMIA or sponsorship). Match bands 85/70/50 shown (Strong/Good/Manual review/Not recommended) and stored; matches below 50 are never auto-proposed; essential vetoes still override. Staff accept/reject at the **match** level (new endpoints, audited) feeding application preparation; job fields gain salary_text, employment_type, required_experience_text, closing_date (nullable).

## 7. Service contracts and the legal-review gate (Task 6)
`fin_service_contracts(candidate_id, service_id (fin_services), agreement_signed_at, signed_document_key, start_date, end_date, refund_terms text, status draft|active|ended|cancelled)` and `fin_legal_reviews(jurisdiction (CA-ON … or country code), service_kind (candidate_fee), status pending|approved|prohibited, reviewer_name, reviewed_at, valid_until, note, evidence_key)`. A `fin_services.kind` of `candidate_fee` (new column, default `standard`) makes the service **billable only when**: (a) a legal review with status `approved` and not expired exists for the candidate's `desired_province` jurisdiction (or home country as configured), (b) an active signed contract exists. Otherwise invoice creation for that service returns 409 with a clear message, and the UI shows "billing disabled — legal review required". Employer-funded arrangements are unaffected. Packages A/B (€250/€550) are entered as services by the owner; no price is preloaded. A prominent note: the platform records reviews, it does not give legal advice.

## 8. NOT built in this stage (and why)
- **Gmail API / OAuth drafts and sends**: needs the owner's Google Cloud OAuth client, consent screen and scopes. Today's SMTP/IMAP adapter and signed inbound webhook remain; a Gmail adapter behind the same interface is a later task once credentials exist (can be built against a fake Gmail server).
- **Job sources (Job Bank feed, LinkedIn, Indeed)**: owner access/terms; no scraping.
- **LLM-written CVs/letters**: no AI provider key; deterministic templates only.
- **NOC/TEER mapping**: needs the official reference data supplied by the owner (the table and lookup can be added when the data file is provided).
- **Prospective-employer outreach without a vacancy**: CASL risk; blocked by the guard until a lawyer approves the basis.
- **Candidate fees**: gate built (§7); the legal opinion is the owner's. Recruiter licensing and immigration-advice questions are flagged, not decided.
- **Tokenised candidate link**: login by e-mail code stays.

## 9. Testing
Real-Postgres tests for each task (reference uniqueness under concurrency, CV generation correctness with text extraction, refusal on missing minimum, no invented content (property-style checks that every output string derives from the input), approval gates, report numbers vs raw SQL, PDF/XLSX parse-back, scoping/isolation, suppression blocking sends, classification evidence rule, billing gate matrix), UI checks and browser smoke, e2e journey, route sweep updates, honest checklist.
